## 0. Rules of engagement

1. **This commit adds one document and nothing else.** No `.csproj`, XAML, service,
   script, workflow, settings or `AGENTS.md` change ships with it.
2. **No repository is created, no remote is added, no tag is pushed, and no release
   is published** until the owner says so. Creating `Fettah010/DevDesk` (O1/D1) is
   an owner action; this plan only describes it.
3. **No global tool install.** `vpk` is pinned and installed per-job (§5, W-0.1.3);
   `dotnet tool install --global vpk` is not part of this plan.
4. **Work-item order is the implementation order.** Each `W-` item is one
   reviewable commit with its own tests. A later item may not be started to unblock
   an earlier one; if it must be, the reorder is written into §12 first.
5. **Scope may shrink, never grow** (roadmap §10.3). Anything discovered that is
   not needed for this release's exit demo is logged in §12 as "deferred to
   vX.Y.Z", not implemented.
6. **A roadmap contradiction is a question for the owner, not a silent choice.**
   §2 and §3 list every one found during research.
7. **Evidence over assertion.** Any claim in §12 needs a command and its output
   (or a screenshot path) next to it.
8. **The user's machine is not the CI machine.** Every "works" statement is
   qualified with where it was observed.

Two more inconsistencies worth naming, because they decide how the release is
demoed:

- **O1 (blocking):** the roadmap's default is a **private** repo until 1.0, but
  `UpdateService` only authenticates with a `GITHUB_TOKEN` **environment variable**.
  An installed app has no such variable, so a private feed cannot be read by the
  very app that is supposed to update itself. Token storage is scheduled for
  **0.5.0**. This is a direct conflict between W-0.1.2 and the exit demo.
- **O2 (blocking):** `release.yml` publishes to **`stable`** on a tag push. Tagging
  `v0.1.0-beta` therefore produces a **stable** release, which no beta client
  reads. The exit demo ("tag `v0.1.0-beta` and let CI publish → the installed app
  finds the update") cannot pass without a tag→channel mapping or a manual
  `-Channel beta` publish.

## 3. Owner decisions required before work starts

Twelve decisions are needed. Four are genuinely blocking (marked **B**); the other
eight are roadmap defaults (or internal fixes) that only need a "yes". If the
answer is "use the recommendation for all", W-0.1.1 and W-0.1.2 can start
immediately.

### 3.1 O1 — Repository visibility vs. self-update **(B, blocks W-0.1.2 / W-0.1.3)**

The roadmap defaults D1 to "private until 1.0". But `UpdateService` builds its
`GithubSource` with a token taken **only** from the `GITHUB_TOKEN` environment
variable (`Services/UpdateService.cs:106`). A launched app has no such variable,
so a private feed returns 404 and the exit demo's whole point — "it updates
itself" — is false. Token storage is a **0.5.0** item (F12).

| Option | What it costs | What it breaks |
| --- | --- | --- |
| **A. Public repo `Fettah010/DevDesk`, releases in the same repo** *(recommended)* | Source becomes public from the first push. Anonymous update check: 60 req/h per IP, enough for one check per launch | Nothing in 0.1.0. It does commit to public history — worth deciding before the first `git push` |
| **B. Private source repo + separate public release-feed repo** | Two repos; `vpk upload github` writes to one repo, so the pipeline needs an asset mirror step plus a second token/scope | Extra moving part in the one release whose job is "prove the pipeline" |
| **C. Private repo, self-update deferred to 0.5.0** | Nothing new | Exit demo loses the update step and §10.5's 0.1.0 sentence ("it updates itself") becomes untrue |
| **D. Private repo + token storage moved into 0.1.0** | Pulls 0.5.0's Credential Manager/DPAPI work forward: PAT entry UI, vault fallback, redaction tests | Real scope increase in an already-L release; needs a §10.3 change-control note |

**Recommendation: A.** The README already claims MIT, the roadmap already wants a
grep test proving no DevDesk code points at the template, and "the app updates
itself" is the rung's whole sentence. If the source must stay private, **C** is
honest and **D** is the priced version of B.

Whichever is chosen, the plan keeps the `GITHUB_TOKEN` override path untouched —
it is a debugging convenience today and gets replaced by real auth in 0.5.0.

### 3.2 O2 — Tag → channel mapping in CI **(B, blocks the exit demo)**

`release.yml` takes `channel` with default `stable`; a `v*` tag push therefore
publishes **every** tag — including `v0.1.0-beta` — to the stable feed. Velopack
keeps one version per channel, and a beta client reads `beta`, so the installed
beta app would find nothing.

| Option | Cost | Verdict |
| --- | --- | --- |
| **A. Derive channel from the tag** — `vX.Y.Z` → `stable`, `vX.Y.Z-beta` → `beta`, `vX.Y.Z-dev` → `dev`; `workflow_dispatch` keeps a choice limited to those three | One mapping function in `build-and-release.ps1` + one step in `ci`/`release.yml`; `alpha` removed | **Recommended.** §10.3 allows adding scope that this release's own exit demo requires |
| B. Keep CI stable-only; publish betas by running the script locally with `-Channel beta` | Zero code | Exit demo step "let CI publish" becomes "run the script"; the workflow stays misleading until 0.6.0 |
| C. Leave it to 0.6.0 (roadmap F11 schedule) | Zero code | The demo cannot be performed as written in this release |

**Recommendation: A**, implemented minimally — the mapping lives in the script
(single source of truth per conventions), and `release.yml` only *calls* it.

### 3.3 S1 — Does 0.1.0 ship a persisted scan cache? **(B, blocks W-0.1.5)**

F7's table row says "0.1.0 (cache)"; W-0.1.5 asks only for an in-memory snapshot;
§3.9 lists `scan-cache.json` with no version.

| Option | Effect |
| --- | --- |

| B. Add **W-0.1.5b**: atomic cache file, schema, staleness, delete-on-mismatch | Honours F7 literally; adds a file format, a TTL policy and ~6 tests to this release |

**Recommendation: A**, with F7 annotated in the roadmap (that annotation is a
roadmap status change, allowed by §10.1, and must not rewrite scope).

### W-0.1.6 — Scan correctness

> *Roadmap acceptance:* new tests: worktree repo detected; self moved/renamed still
> detected; `bin/obj` not walked; cancellation returns quickly; 8-repo scan < 1.5 s.

**Goal.** Fix the six correctness gaps in F6 and make the scan bounded, cancellable
and deterministic. R2 makes the worktree case real today, not hypothetical.

**Files.** `Services/ScanEngine.cs`, `Services/GitRunner.cs`,
`Models/ProjectModel.cs`, `Models/ScanProgress.cs` (new),
`Services/SelfLocator.cs` (new), `Services/PathHygiene.cs` (new),
`Services/SettingsService.cs` (default ignores only),
`DevDesk.Tests/ScanEngineTests.cs` (new), `DevDesk.Tests/GitRunnerTests.cs` (new).

**Steps.**
1. **Repo detection:** a folder is a repo when `.git` is a **directory or a file**
   (worktrees, submodules). Confirmed against the three real worktrees in
   `copilot-worktrees`.
2. **Self discovery:** walk up from `AppContext.BaseDirectory` for `.git`, stop at
   the drive root, and treat "installed under `%LocalAppData%\DevDesk\current`"
   as *no source repo*. Exclusion is by **canonical path**, never by the literal
   name `DevDesk`, so renaming or moving the checkout keeps working. If no repo is
   found, `Self` is null and the DevDesk page shows install information instead of
   a phantom card.
3. **Hygiene:** `CountUnder` (and the walk) skips `bin`, `obj`, `node_modules`,
   `.vs`, `Releases`, `Logs`, `.git`, dot-folders and reparse points; caps depth and
   file count so one huge folder cannot stall the scan.
4. **Determinism:** select `<FolderName>.csproj` if present, else the
   alphabetically-first `*.csproj`; never `FirstOrDefault()` on an unordered
   directory listing.
5. **Cancellation + progress:** `CancellationToken` on every public async call;
   `IProgress<ScanProgress>` reports (completed, total, current name); a cancelled
   scan leaves no half-populated snapshot.
6. **Parsers:** `TrimEnd('\r')` per line instead of trimming the whole output
   (leading whitespace is meaningful in porcelain v2); unquote paths when git
   escapes them.
7. **Git invocation:** `--porcelain=v2`, `-c core.quotepath=false`,
   `--no-optional-locks`, `-c color.ui=false`, `--no-pager`, plus
   `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never` so a scan can never hang on
   a credential prompt. Read ahead/behind from porcelain v2's `# branch.ab` header
   instead of a second `rev-list` process (a real time saving).
8. **Bounded parallelism:** repos scanned concurrently, capped at
   `min(4, Environment.ProcessorCount)`; results reassembled in stable order.
9. **Ignore `copilot-worktrees` by default (D8) in this same commit**, so the
   newly-working worktree detection does not add three ghost cards.

**Done when.**
- All six acceptance cases have a test.
- A cancellation during a scan returns in well under a second and triggers no git
  process.
- A cold scan of the real 6-repo ecosystem is measured and recorded (target
  ≤ 1.5 s, R3). The number is reported, not asserted in CI.

**Tests.** `Scan_DetectsGitFileWorktree`, `Scan_IgnoredFolderYieldsNoCards`,
`Scan_SelfFoundWhenFolderRenamed`, `Scan_SelfNullWhenInstalled`,
`Scan_SkipsHygieneFolders`, `Scan_SkipsReparsePoints`,
`Scan_CancellationReturnsPromptly`, `Scan_ProjectFileIsDeterministic`,
`Scan_PorcelainV2ParsesCrLf`, `Scan_IsReadOnly` (timestamps + clean status before/after),
`GitRunner_NeverPromptsForCredentials`, `Scan_RealEcosystem_ReportsDuration`
(`[Trait("Category","Perf")]`, generous ceiling, skipped in CI).

**Not in this item.** No file-system watchers, no multi-root, no persisted cache,
no semantic version comparison, and **no worktree → main-repo identity merge**

is what the exit demo checks.

| --- | --- | --- |
| **Velopack channel** | `stable \| beta \| dev` — which feed a client reads; one version per channel | `releases.<channel>.json` in the GitHub release, `UpdateOptions.ExplicitChannel` |
| **GitHub "prerelease"** | A UI flag on a release; `GithubSource(prerelease:false)` **ignores** those releases entirely | `vpk upload github --pre` |
| **Prerelease suffix** | `-beta` in `v0.1.0-beta` / `0.1.0-beta`; a *version* label | csproj `InformationalVersion`, tag name |
| **Settings `schemaVersion`** | Integer inside `settings.json`; `1` is the first real schema | `Models/AppSettings.cs` |

Rule: the version suffix selects the **channel**, the channel selects the
**feed**, and the feed must never be marked as a GitHub prerelease — otherwise
the client that needs it is the one that cannot see it (P4).
