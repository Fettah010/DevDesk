## 1. Goal and release boundary

DevDesk can display current GitHub repository information, published releases,
Actions runs, and open pull requests for relevant local repositories. Users may
optionally authenticate with a personal access token (PAT) so private
repositories and the authenticated rate budget can be read. The token is stored
only in an OS-protected credential store; it is never serialized into settings,
cache, logs, diagnostics exports, process arguments, or UI text.

This is a **read-only integration**. The client exposes only HTTP GET operations;
refresh means re-reading data, not triggering a workflow. It cannot create or
edit a repository, create a release, cancel or re-run a workflow, or modify a
pull request. These are explicit non-goals, not deferred controls.

**Exit demo:** after explicitly opening GitHub or requesting refresh, a user can
inspect real repository, release, workflow-run, and PR data; open a run in the
browser; then go offline and still see clearly marked cached data. No GitHub
request is made during startup or the local project scan.

## 2. Research findings and constraints

| Finding | Design consequence |
|---|---|
| GitHub's REST API uses `Accept: application/vnd.github+json`, a `User-Agent`, and a dated `X-GitHub-Api-Version`. The current REST docs identify `2026-03-10`. | Centralize and test headers in one HTTP client; pin the API version intentionally and update it only with fixture/API review. |
| The public REST API rate limit is 60 requests/hour per source IP; authenticated PAT traffic is normally 5,000/hour. Conditional requests that return `304 Not Modified` do not consume the primary rate limit. | Cache first, send `If-None-Match` when an ETag exists, and report the server's actual remaining/reset budget rather than estimating it. |
| `GET /repos/{owner}/{repo}/actions/runs`, `GET /repos/{owner}/{repo}/releases`, and `GET /repos/{owner}/{repo}/pulls` provide the required read surfaces. | Keep one explicit GET-only service surface. Use bounded page sizes; do not download logs or enumerate all pages for a summary UI. |
| `/user` validates that a token authenticates an account, but a successful response does **not** prove that the token has every repository permission; without `read:user`, GitHub may return only the public profile. | Explain token validity separately from access to each repository. Do not claim a scope has been granted based only on `/user` returning 200. |
| A repository URL can be HTTPS, SSH URI, or SCP-like SSH syntax. GitHub Enterprise hostnames are not equivalent to `api.github.com`. | Parse local remotes without network access. Only enrich `github.com` in this release; enterprise identities may still open in a browser but receive no GitHub REST calls. |
| Release tags already have one vocabulary: `stable`, `beta`, `dev` in `ReleaseChannels`. | Classify releases with `ReleaseChannels.TryParseTag`; never add a second channel parser or infer a channel from the prerelease boolean alone. |
| The local scanner is deliberately fast, read-only, and offline. | GitHub enrichment is lazy and page-driven; it cannot be added to `ScanEngine`, `ProjectCatalog`'s scan path, or startup. |

### Confirmed decisions

1. Use `HttpClient` and `System.Text.Json`; do not add Octokit or another client
   dependency.
2. The GitHub.com REST API is the only enrichment host in 0.5.0. GitHub
   Enterprise Server/API base URL discovery and authentication are out of scope.
3. PAT is the 0.5.0 sign-in method. OAuth/device flow is not added.
4. Follow roadmap §3.9 for credential protection: Windows Credential Manager
   (`PasswordVault`) as the primary store and DPAPI-protected fallback only if
   the primary store is unavailable. Verify this app's unpackaged WinUI runtime
   supports the primary store before wiring it. If neither secure store works,
   report the failure and do not save the token.
5. Cache is per repository/resource, has a five-minute freshness window, uses
   conditional revalidation, and is purged on sign-out or credential change.
6. Only data for the current visible/relevant GitHub page or explicitly selected
   repositories is fetched. Startup must perform zero GitHub requests.

### Open implementation checks (not user-facing design changes)

- Confirm the desktop app can use `PasswordVault` under its actual unpackaged
  execution model; exercise both primary and DPAPI fallback paths with injected
  store implementations.
- Derive the precise least-privilege PAT instructions from the endpoint
  permissions documented at implementation time. The UI must distinguish
  missing access, invalid authentication, rate limiting, and offline failure.
- Confirm WinUI browser launching follows the existing safe-open conventions
  and only accepts validated HTTPS GitHub web URLs.

### 3.1 Explicit non-goals

- Any GitHub mutation: repository creation, release creation, issue/PR writing,
  workflow rerun/cancel, or other POST/PATCH/PUT/DELETE call.
- Enterprise API host configuration or enterprise token storage.
- OAuth or device flow.
- Notifications, issue management, GitHub logs/artifact downloads, cloning, or
  background polling.
- A new generic plugin/network framework or new package dependency.
- Making GitHub calls from `ScanEngine`, `ProjectCatalog`, application startup,
  or the release updater's existing token environment-variable path.
- Release publishing or version bumping; those belong to v0.6.0.

## 4. Contracts and behavior

### 4.1 Repository identity

`GitHubRepositoryIdentity` contains the normalized host, owner, and repository
name, plus an explicit predicate for GitHub.com enrichment. It is derived from a
single remote URL only; selection among fetch remotes belongs to the caller.
Unsupported/missing remotes return no identity and cause no HTTP request. The
parser is pure and must not silently convert an enterprise hostname into the
public API host.

### 4.2 Service boundary

The GitHub service accepts a validated identity and exposes asynchronous
read-only methods. It does not expose a raw `HttpClient` or a generic request
method to pages. All calls accept cancellation; failures are typed and preserve
the distinction between:

- no credential / invalid credential;
- repository not found or inaccessible;
- insufficient permission;
- primary/secondary rate limit;
- network/offline/timeout;
- malformed or unexpected response.

Pages may show stale cached data for network failure, but must show an explicit
stale/offline marker. A 401/403/404 is not an offline result. Error messages must
not include authorization headers, PATs, or unredacted query values.

### 4.3 Release channel classification

Use the shared `ReleaseChannels.TryParseTag` implementation. A release appears
in a channel only if its tag parses into one of `stable`, `beta`, or `dev`.
Unknown suffixes are shown only in an explicitly unclassified/other state or
omitted with an honest count; they are never coerced into a channel. GitHub's
`prerelease` flag may be displayed as API metadata, but it does not replace the
project's channel rule.

### 4.4 Cache and requests

- Cache key: normalized GitHub.com owner/repository plus resource and query
  parameters that change the response.
- Store response payload, ETag, fetch time, and the validated account identity
  when the request used authentication; never store the token or request headers.
- Cache writes are atomic and bounded. Malformed or incompatible cache data is
  ignored with a diagnostic warning; it must not block opening GitHub.
- At five minutes, render cached data immediately and revalidate on explicit
  refresh or when the resource is selected. Send `If-None-Match`; on 304 retain
  the payload and advance its validation timestamp.
- On a network failure, keep the last valid payload with a stale marker. On
  credential/account change, sign-out, or cache schema mismatch, do not reuse
  data from the previous authentication context.
- Honor `Retry-After` and primary reset headers. Do not spin retries; one
  bounded retry is allowed only when the server gives a future retry time and
  the user remains on the relevant surface.
- No infinite pagination: use a small documented page size for the UI, with an
  explicit "more on GitHub" link rather than fetching all historical data.

### 4.5 Secrets and diagnostics

- Token entry is masked, never prefilled from storage, and cleared from the
  editor after save/validation.
- No PAT in `settings.json`, `github-cache.json`, argv, environment mutation,
  Serilog properties, diagnostics ring/file/export, exceptions, or test output.
- Do not log full request headers or raw response bodies. Log endpoint category,
  status code, elapsed time, and safe rate-limit metadata only.
- Tests use synthetic token strings and fake HTTP; no GitHub network dependency.
- Diagnostic export remains redacted and excludes the OS credential store.

## 5. UX state matrix

| Surface state | Required behavior |
|---|---|
| First visit / no token | Explain that public repositories can be read without sign-in and private access needs a PAT; show real public data only after user opens or refreshes the surface. |
| Signed in | Show account identity, credential status, and a visible sign-out action. Do not imply that sign-in guarantees access to every repository. |
| No local GitHub remotes | Empty state explaining that no GitHub.com repository is available; no example/demo rows. |
| Enterprise or other host | Show local identity and offer safe browser opening where supported; say API enrichment is unsupported in v0.5.0. |
| Loading | Busy indicator and the selected repository/resource; cancel work when selection changes. |
| Fresh data | Data plus last-checked timestamp; no stale/offline wording. |
| Stale cache, network unavailable | Keep cached rows and show "Offline — cached at …"; offer retry. |
| 401 | Explain that the token is invalid/revoked; do not discard it silently. Offer replace/sign-out. |
| 403 | Explain insufficient access or rate limiting based on response headers; do not describe as network failure. |
| 404 | Explain unavailable/not found without leaking whether a private repository exists to an unauthenticated viewer. |
| Rate limited | Show remaining/reset when known; disable repeated refresh until safe; retain cache. |
| Empty resource | State "No published releases/open pull requests/workflow runs" only after a successful API response. |
| Unexpected failure | Show a concise message and preserve any last valid cache; diagnostic details stay secret-safe. |

Run, release, and PR links open the API-provided `html_url` only after validating
HTTPS and an allowed GitHub.com host. The UI must not build a browser URL by
concatenating untrusted API fields.

## 7. Test plan

Tests remain in `DevDesk.Tests/`; fixtures use fake handlers, temporary
directories, synthetic tokens, and injected clocks. No test makes a network call
or reads this machine's Credential Manager.

| Area | Coverage |
|---|---|
| URL identity | HTTPS, `.git`, slash/casing, SSH URI, SCP-like SSH, enterprise host, malformed URL, local path, extra path, encoded separator, missing remote; unsupported hosts never produce an API base URL. |
| Credential store | save/read/remove, unavailable primary store, DPAPI fallback, both stores unavailable, restart behavior via fake store; input values are not reflected in result strings. |
| HTTP contract | expected headers, GET-only, safe path escaping, cancellation, timeout, response size bounds, error categories, malformed JSON. |
| ETag | cold 200/cache write, subsequent `If-None-Match`, 304 reuses body, expired cache refresh, server ETag replacement. |
| Rate behavior | remaining/reset headers, `Retry-After`, primary limit, secondary 403, no retry loop, cache retained during a limit. |
| Cache and offline | atomic write, schema mismatch, corruption, TTL, stale presentation, account/token-change purge, no sensitive strings in serialized files. |
| API DTOs | repository, release/assets, run/status/conclusion/branch, PR/draft/check summary fixtures; tolerate nullable/unknown fields. |
| UI/source contracts | empty/auth/stale/error states, no fake rows, safe links, settings exclude secrets, app startup and local scan make zero GitHub requests. |
| Security regression | synthetic credentials, protected fallback, cache purge, and safe error paths; startup/scan source guard prevents eager GitHub calls. |

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| PAT appears in persistent data or logs | OS-protected credential boundary; synthetic-secret regression scans across settings/cache/log/export and safe error formatting. |
| `PasswordVault` unavailable to unpackaged desktop app | Verify before wiring. DPAPI-protected fallback only; fail closed if neither secure path is available. |
| Token validates but lacks repository permissions | Separate `/user` identity validation from per-repository authorization; explain permissions without false scope claims. |
| Private repo 404 misread as missing project | Preserve auth context and present neutral "not found or inaccessible" state. |
| API schema changes | Fixture-driven DTO parsing, nullable fields, tolerant unknown-field handling; don't deserialize API payload into UI types directly. |
| Secondary rate limit / repeated refresh | ETag cache, per-resource single-flight, request budget, respect retry headers, no automatic polling. |
| Enterprise host sent to public API | Exact GitHub.com host classification; no API enrichment for other hosts. |
| 0.5.0 work collides with active 0.4.0 changes | Isolated pure parser first; no cross-version integration refactor until current uncommitted work is settled. |
| Scope expands into release actions | GET-only service contract and explicit non-goals; v0.6.0 owns publication workflow. |
