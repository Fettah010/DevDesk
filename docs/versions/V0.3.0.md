## 1. Goal

A developer selects a repository in DevDesk, presses **Build**, and reads the
result — warnings, errors, exit code, duration — without a terminal. They can
**run** it (and stop it), **publish** it, click an error to open the file at the
line, and see what happened ten minutes ago after a restart.

This is job **J3** in the roadmap ("change code → build/run and read the errors
without a terminal"), and it is the prerequisite for the template smoke build
(0.4) and release verification (0.6). Nothing here may weaken the two promises
the app already keeps: **the scan never writes or touches the network**, and
**no command runs without the user knowing exactly what it does**.

Exit state of this version, in one sentence: *every .NET project in the
ecosystem either builds from DevDesk or says precisely why it cannot, and every
build that ran is still inspectable after a restart.*

## 3. Decisions this work order resolves

Numbered so the implementation can cite them and a reviewer can disagree once.

| ID | Decision | Why |
| --- | --- | --- |
| **D-0.3.1** | **Build state is not scan state.** `ProjectModel` is unchanged; pages join `BuildHistory.LastFor(path)` for a badge. | Roadmap invariant 5 ("a scan never writes"); a scan result that contains "last build" would make the snapshot depend on a process that already ran. |
| **D-0.3.2** | **Run = ensure build, then launch the resolved exe.** `dotnet run --project …` is the fallback when no output exe can be resolved. | A launched exe is a process we own and can stop (tree kill); `dotnet run` re-enters MSBuild and can leave a child nobody holds. Stdin is not redirected, so an app that reads console input sees EOF — documented, not hidden. |
| **D-0.3.3** | **Publish never passes `-o`.** The output folder is MSBuild's own publish directory; the path is read from the `-> …` line in the output, with a computed default as fallback. | Writing to a chosen folder inside a repo can dirty it; the project file owns packaging, the UI owns configuration and platform. |
| **D-0.3.4** | **One build at a time, process-wide.** Further requests become real `Operation` rows with status `Queued`. | Two concurrent `dotnet build` runs on the same `obj/` corrupt each other. A queued row is honest; a second hidden run is not. |
| **D-0.3.5** | **The console is bounded, the file is complete.** UI keeps the last 20,000 lines and states how many earlier lines it is not showing; the full log is always on disk. | 100k-line builds must stay responsive without the UI pretending it has everything. |
| **D-0.3.6** | **"Run tests" on the DevDesk page is one fixed profile** (`dotnet test DevDesk.Tests -p:Platform=x64`), not a test-runner UI. | Roadmap excludes a test-runner UI from 0.3; a fixed, previewed command is the honest middle. |
| **D-0.3.7** | **Opening a problem is best-effort, the data is not.** Order: `code --goto file:line` → `devenv /edit file` → default app. The row always shows `file:line:col` and a Copy action. | Not every machine has a line-aware editor; the line number must not be lost when the jump is not possible. |
| **D-0.3.8** | **Activity is a footer flyout *and* an 8th route.** The page is the history; the flyout is the last ten; the title bar shows only what is running. | Roadmap §5.1 + W-0.3.6; a flyout alone loses history on a restart, a page alone is two clicks away from a build that just failed. |
| **D-0.3.9** | **Platform is passed only when the project understands it.** `-p:Platform=x64` is added when the csproj declares `<Platforms>` containing the value or references WindowsAppSDK; otherwise the profile shows platform as not applicable. | `-p:Platform` on a project with no such platform is a build failure invented by the UI (AGENTS gotcha 2). |
| **D-0.3.10** | **One owner per number** (gotcha 15): `PerfCounters.RecordBuild` owns the process-wide build count/duration; `BuildHistory` owns the per-project badge; `ActivityCenter` owns queue state. No copies. | Three counters for "how many builds" is three truths. |
| **D-0.3.11** | **No new NuGet dependency.** `System.Diagnostics.Process`, `System.Text.RegularExpressions`, `System.Text.Json`. | Roadmap §6.6: a dependency needs a named job and a removal story; none of these three need replacing. |
| **D-0.3.12** | **The relaunch waits in the launcher, not in the new process.** `launch-dev.ps1` gained `-WaitForProcessId`; the app starts it with its own pid and exits at once. | Measured: a `dotnet build` started while DevDesk runs fails with MSB3027 (`DevDesk.exe`/`DevDesk.dll` locked by this process), so "build first, then start the new exe" cannot work when a source changed — the only case the button exists for. The launcher is a different process, so it can wait for the pid, build, and then start the app through the normal single-instance flow. |

## 5. Contracts

### 5.1 `IProcessRunner` (Infrastructure)

```csharp
public enum ProcessOutcome { Succeeded, Failed, Canceled, TimedOut, NotFound }

public sealed record ProcessRequest(
    string FileName,
    IReadOnlyList<string> Arguments,      // argument list only — never a command string
    string WorkingDirectory,
    IReadOnlyDictionary<string, string>? Environment = null,
    TimeSpan? Timeout = null);

public sealed record ProcessOutputLine(string Text, bool IsError, DateTimeOffset At);

public sealed record ProcessResult(
    ProcessOutcome Outcome,
    int ExitCode,
    string StandardErrorTail,
    TimeSpan Duration,
    string? FailureHint);

public interface IProcessRunner
{
    Task<ProcessResult> RunAsync(
        ProcessRequest request,
        IProgress<ProcessOutputLine>? output,
        CancellationToken cancellationToken);
}
```

Rules, all testable:

1. `ProcessStartInfo.ArgumentList` only; `UseShellExecute = false`,
   `CreateNoWindow = true`, stdout/stderr redirected, UTF-8.
2. `WorkingDirectory` must exist before start, else `NotFound` with
   "the folder does not exist" (never an exception).
3. `OutputDataReceived`/`ErrorDataReceived` line events; no polling, no
   `ReadToEnd` on a long build.
4. Cancel and timeout both `Kill(entireProcessTree: true)`, drain the pipes, and
   report `Canceled` vs `TimedOut` distinctly (a cancel is not a failure).
5. A `Win32Exception` at start is `NotFound` + hint ("dotnet was not found on
   PATH"), because that is the common real cause.
6. Environment: `DOTNET_CLI_TELEMETRY_OPTOUT=1`, `DOTNET_NOLOGO=1`,
   `DOTNET_CLI_UI_LANGUAGE=en` (stable diagnostic shapes), plus caller values.
7. The runner logs executable + arguments (redacted) at INF and the exit code;
   output goes to the build log file, not the app log.

### 5.2 `BuildService`

| Method | Behaviour |
| --- | --- |
| `ResolveProfileAsync(ProjectModel)` | Target via `FindSolutionOrProject`; platform applicability (D-0.3.9); settings defaults merged with the per-project override. |
| `BuildAsync(request, progress, ct)` | `dotnet build <target> -c <cfg> [-p:Platform=…] [--no-restore] [extra args]`, 30 min timeout. |
| `RunAsync(request, progress, ct)` | Build first (unless `--no-build` was chosen and an exe exists), then start the resolved exe; no timeout; Stop kills the tree (D-0.3.2). |
| `PublishAsync(request, progress, ct)` | `dotnet publish <target> -c <cfg> [-p:Platform=…]`, output folder parsed from `-> …` (D-0.3.3), 30 min timeout. |
| `TestSelfAsync(...)` | The single fixed profile from D-0.3.6. |

`BuildService` never decides *what* the user wants (the VM does), never touches
XAML, and never runs two builds at once (D-0.3.4). It reports through
`ActivityCenter` and `PerfCounters`; it does not keep its own history.

### 5.3 `ActivityCenter`

```csharp
public enum OperationStatus { Queued, Running, Succeeded, Failed, Canceled }
public enum OperationKind { Build, Run, Publish, Test }

public sealed record Operation(
    string Id, OperationKind Kind, string ProjectName, string ProjectPath,
    string Title, string Command, OperationStatus Status,
    DateTimeOffset QueuedAt, DateTimeOffset? StartedAt, DateTimeOffset? FinishedAt,
    int? ExitCode, string? FirstError, string? LogPath, bool CanRetry);
```

- Owns the queue and the one-at-a-time gate; raises `Changed` with an immutable
  snapshot list.
- Cancel: `Queued` → removed with status `Canceled`; `Running` → cancel token,
  tree kill, `Canceled` (never `Failed`).
- Retry creates a **new** operation with the same request (never reuses an id).
- History is the last 200 in memory, mirrored to `build-history.json`.
- No UI types, no dispatcher: the VM marshals.

### 5.4 Persistence

| File | Location | Shape | Rules |
| --- | --- | --- | --- |
| `build-history.json` | `SettingsService.ResolveDataDirectory()` | `{ schemaVersion: 1, writtenAt, entries: [ … ] }` | Atomic via `JsonStore`; ring 200; unknown schema → discard + rebuild; corrupt → backup + defaults (never a startup failure). |
| `Logs\builds\<yyyyMMdd-HHmmss>-<kind>-<project>.log` | same root (honours `DEVDESK_DATA_DIR`) | plain text, one line per event | Full output, including lines the console dropped; deleted with the log retention rule (14 days) or by the user. |

Settings additions — **additive, `schemaVersion` stays 1** (roadmap §4.3 policy):

```json
"build": {
  "configuration": "Debug",
  "platform": "x64",
  "noRestore": false,
  "followTail": true,
  "wrapLines": false,
  "historyLimit": 200
},
"buildProfiles": {
  "C:\\Code\\projects\\DevEcosystem\\Formixa": {
    "configuration": "Release",
    "platform": "x64",
    "target": "Formixa.csproj",
    "extraArgs": ""
  }
}
```

Rules: path keys normalized (full path, no trailing separator, case-insensitive
compare); an unknown key survives a save; a missing profile falls back to
defaults; nothing here is ever a secret.

### 5.5 Problem parsing

One parser, code-first (localized prose is not a contract):

```
^(?<file>[^(]+)\((?<line>\d+)(,(?<col>\d+))?\):\s*(?<sev>error|warning)\s*(?<code>[A-Za-z]{1,4}\d{3,5})?:\s*(?<msg>.*)$
```

- Second shape (no file/line): `: error CS1002: ; expected [C:\…\Formixa.csproj]`.
- The trailing `[project]` is stripped from the message and kept as context.
- Severity is `error`/`warning` only; "0 Warning(s)" summary lines are ignored.
- Dedupe identical `(code, file, line, message)`; cap the list at 500 with a
  "showing first 500 of N" row.
- Multi-line messages: a continuation line (no diagnostic prefix) appends to the
  previous problem.

## 11. Risks

| Risk | Mitigation |
| --- | --- |
| Output volume janks the UI | Line events batched to the dispatcher (≤ 100 ms), virtualized list, bounded buffer (D-0.3.5); measured against the 100k-line case. |
| Orphaned build/run processes | Tree kill on cancel/timeout; a `JobObject` only if the tree kill proves insufficient (then it becomes its own work item with a test). |
| `dotnet`/MSBuild first-run warmup looks like a hang | No restore spinner until 2 s; hint "first run may take a minute"; 30 min timeout, not 30 s. |
| Localized MSBuild prose | Parse codes and the `file(line,col): error CODE:` shape only (§5.5); prose is never matched. |
| `-p:Platform` on a project without platforms | D-0.3.9: the property is only passed when the project declares it. |
| Publish writing into a repo and dirtying it | D-0.3.3: no `-o`; output stays in the project's own publish folder; the scan already ignores `bin/obj`. |
| Self relaunch loops | D-0.3.12: the launcher waits for the old pid with a bounded timeout (30 s), then builds and starts; a pid that never exits ends the relaunch instead of stacking a second window. |
| Activity route breaks the shell smoke test | `smoke-ui.ps1` updated in the same commit (W-0.3.9); `MaxScans` unchanged proves Activity does not scan. |
| Build history becomes a second source of truth | D-0.3.10: badges read `BuildHistory` only; `PerfCounters` counts operations, never projects. |
