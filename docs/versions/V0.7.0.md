## Implementation progress

The following foundations are implemented in the current working tree:

- Ordered, enabled multi-root settings with per-root depth and ignore rules;
  root add/enable/reorder/remove controls and visible missing/UNC status.
- Root-relative glob matching with ordered negation and protected Git metadata;
  checkout-path deduplication and local worktree identity/badges.
- Schema-v2 scan-cache persistence, cached/stale/fresh state, cache-first
  Dashboard and Projects rendering, checkout-targeted watcher refresh with
  root reconciliation fallback, partial-root retention, and diagnostics.
- Progressive immutable catalog snapshots with real pending project cards,
  cancellation, stable final ordering, and per-root refresh.
- In-memory search/sort over repository facts and user tags; persistent pins,
  coloured tags, saved views, archive state and recently-opened ordering;
  explicit workspace solution/project discovery and safe open actions.
- Shared ignore-rule evaluation and Settings preview; per-root/folder
  diagnostics for inaccessible locations.
- A separate opt-in FlaUI UI-test project and local runner; the expanded
  isolated UI journey covers search, pin persistence and ignore preview. Core
  CI remains headless, and restore/build/test shares build outputs.

Implementation coverage is substantially broader, but v0.7 is still not
release-ready. Repeated desktop measurements miss M1, M2, and M6. The latest
warm 100-project run loaded the cached snapshot at 221 ms, marked the first
project-card layout ready at 690 ms, and had UI Automation observe the
interactive card at 875 ms (M1 target <700 ms). The native window became
visible after 550 ms (M2 target <400 ms); the internal activation mark is not
substituted for visible-window evidence. Working set was 253 MiB (M5 passes).
The M6 heartbeat recorded a 477 ms maximum delay (target <50 ms) during a mixed
startup/scan/navigation journey that includes UI Automation activity, so
operation-level attribution remains open. Two runs of the retained startup
flow measured window visibility at 538–550 ms, app-side card layout at 684–690
ms, UIA card observation at 864–875 ms, and heartbeat delay at 477–547 ms. M4
passed at 1,855.7 ms with the installed Git executable first on PATH and
default parallelism four, but the host's bundled Git produced substantially
slower results; this environment dependency must remain explicit.
Checkout-only watcher refresh is implemented; installed-path validation and
accessibility/manual review also remain outstanding.

## 1. Goal and release boundary

Make DevDesk useful across several user-selected local repository roots and a
larger project set, without replacing the existing single-catalog architecture.
On launch, a validated cached snapshot should make the project list useful
quickly; a fresh local scan then corrects it. Search, filtering, organization,
and root configuration must operate on real catalog data and persist only the
user's explicit choices.

The scanner remains local and read-only. It must not fetch, push, change a
repository, follow junctions/symlinks outside a root, call GitHub on the startup
path, or silently treat stale cached metadata as current. A failed root or
repository is a visible partial result, not a false empty success.

This work order covers the nine roadmap items W-0.7.1 through W-0.7.9. It does
not add new product pillars or move v0.8 command-palette/tray work or v0.9
release-candidate hardening into this version. Implementation is proceeding
against the accepted v0.7 boundary; unverified criteria remain explicit below.

### Confirmed constraints

1. The repository roadmap's v0.7 scope is the contract: multi-root settings,
   ignore rules, worktree/submodule identity, incremental cache/watcher,
   progressive scan, search/filter/sort, organization, workspace expansion, and
   large-root guards.
2. Keep scan reads offline and read-only. Network roots are not a new supported
   provider; if encountered, report the limitation clearly rather than
   presenting incomplete state as a clean result.
3. Keep all filesystem, Git, watcher, and cache operations in testable services.
   XAML/pages bind and forward commands; they do not own scan logic.
4. Preserve current project behavior for the default ecosystem root and the
   DevDesk self workspace. Do not turn DevDesk into an ordinary project card.
5. Cache is an optimization, never the source of truth. A cache miss, stale
   entry, parse error, access failure, or interrupted write must not block a
   fresh scan or erase valid user settings.
6. No telemetry, cloud roots, cross-repository dependency graph, or new GitHub
   calls are introduced.

## 4. Proposed contracts and behavior

These contracts make the roadmap implementable while preserving current
architecture. Values marked “decision” in §2 stay provisional until accepted.

### 4.1 Root configuration

- Keep one ordered list of root settings under `AppSettings.Roots`; extend
  `ScanRootSettings` rather than adding a second root registry.
- Each configured root has a canonical full path, depth constrained to the
  existing settings range, enabled state, and its own ignore rules.
- Reject empty/invalid paths and duplicate canonical roots on user entry. Do not
  silently normalize a typo into the default ecosystem root.
- Preserve the existing default root and its current safe behavior on upgrade.
  Removing or disabling the final usable root must leave the user a recovery
  path to add/enable one; do not silently restore it in a way that discards
  intent.
- Validate existence and access at scan time, not only when the Settings page
  saves. A missing root remains configured and gets an explicit status so a
  removable drive can return later.
- Reordering roots changes stable discovery precedence, not repository identity.
- Existing BuildHistory and build-profile keys remain keyed to a checkout path;
  root configuration does not rewrite those records.

### 4.2 Ignore matching and traversal safety

- Use one shared matcher for scan traversal and settings preview; do not duplicate
  exclude logic in XAML or marker-count code.
- Match normalized root-relative Windows paths consistently; compare
  case-insensitively and normalize both slash forms.
- Evaluate ordered exclusions and negations as documented in the UI. Invalid
  patterns are rejected with a visible validation message; they do not silently
  become broad excludes or allow-all.
- Keep safety rules outside the user matcher: never descend into `.git`
  metadata, never follow a reparse point, and never escape the configured root.
- Apply configured depth to each root. Stop descending once a repository or
  project-marker folder has been accepted, retaining current behavior unless
  tests demonstrate that nested project discovery needs an explicit rule.
- Dot-folder handling must be reconciled with user-configurable ignores by the
  decision in §2; no blanket rule may be bypassed accidentally by matcher order.

### 4.3 Repository identity

- Distinguish **checkout path** (the worktree that can be opened/built) from
  **common repository identity** (shared Git history/config for linked
  worktrees).
- Canonicalize paths with the existing Windows case-insensitive path semantics.
  Do not identify repositories by folder name, remote URL alone, or branch name.
- Treat pointer parsing as untrusted local file input: validate syntax, resolve
  relative paths deterministically, detect loops/escapes, and convert failures
  to per-item diagnostics rather than exceptions that abort all roots.
- Never run a network Git command to resolve identity. Use local Git metadata
  and existing `GitRunner` argument-list/cancellation/timeout patterns.
- Keep a stable `ProjectModel.Path` for each checkout so existing open/build
  operations continue to target the intended working tree.

### 4.4 Cache and freshness

- Use a dedicated cache DTO with the roadmap's schema-v2 identifier; do not
  serialize `ProjectModel` directly as a long-lived file contract. The cache
  does not exist in the current checkout, so only add a v1 migration if an
  already-shipped cache format is verified before implementation.
- Store only catalog-derived local data: root/checkout identity, project facts
  needed for card paint, self/template separation, capture time, and schema
  version. Exclude credentials, tokens, GitHub API data, logs, build records,
  and arbitrary file contents.
- Cache writes are atomic and bounded. Validate schema, path containment,
  record counts, and required fields before using any entry. A future schema is
  ignored with a warning and rebuilt by scanning.
- Render a valid prior cache as **cached / last checked at ...**; do not label it
  current or let it overwrite a newer successful scan. Then refresh locally in
  the background. If refresh fails, preserve the last good cache with an
  explicit stale/error state.
- Cache must be disposable: deleting it changes startup time only, not project
  settings, build history, or source repositories.
- Watchers are hints, not a correctness authority. Coalesce event storms;
  overflow, watcher disposal, inaccessible roots, or unsupported locations
  schedule a full root reconciliation instead of dropping changes.
- On shutdown/dispose, cancel scan work and dispose every watcher/timer. No
  watcher may keep the process alive or leak callbacks into a disposed page.

### 4.5 Progressive catalog and UI state

- Continue to expose one catalog to all consumers. Partial events must carry
  root identity, progress counts, and the affected project data; callers must
  not infer “complete” from an empty collection.
- Represent cache hydration, fresh scan completion, partial scan, and scan
  failure as distinct catalog freshness states. A cache snapshot can satisfy
  first paint but cannot satisfy the “fresh scan completed this process” test
  used by `GetOrRefreshAsync`; the first page visit must start or join
  background revalidation without blanking cached cards.
- Preserve a last-good complete snapshot while scanning. Define whether
  progressive updates are a separate view or immutable partial snapshots before
  implementation; never mutate a snapshot already held by another page.
- Each visible card is backed by a real project model, whether it came from a
  validated cache or completed local Git reads. Skeletons are not fake project
  rows and must not count in project totals.
- Dashboard and Projects search/sort are projections over the catalog; they do
  not trigger scans. Root changes and watcher invalidations flow through the
  catalog and update all pages consistently.
- Keep page unload/navigation from cancelling confirmed catalog work; cancel
  only on explicit user action, app shutdown, or a superseding catalog policy.
- All asynchronous UI updates return to the dispatcher. Never block the UI
  thread on a scan, Git call, file write, watcher stop, or cache read.

### 4.6 Search and organization

- Search only fields with real values in the model: display name, path, branch,
  and version. Do not imply support for tags/remote data unless the model
  actually contains and refreshes those facts.
- Sorting options must define stable ties. Keep pin/favorite priority and
  configured root order ahead of secondary name/activity/health/version keys
  only after the owner confirms the ordering contract.
- Saved filter definitions and pins/tags are user-owned metadata, not
  `ProjectModel` scan facts. Use stable checkout paths and tolerate paths that
  disappear or move.
- “Recently opened” is updated only after an existing open action succeeds.
  “Hide archived” must not guess from a branch name; define a reliable
  repository state or defer that toggle while preserving the roadmap intent.
- Colour and tag selection should use the existing theme resources and
  accessible text/automation names; colour alone never conveys status.

### 4.7 Workspace expansion

- Reuse existing marker discovery / `ProjectOpenActions` where possible.
- Enumerate recognized solutions/projects on demand and keep the existing
  `ProjectModel.Components` boundary. Do not recursively crawl arbitrary source
  trees on the UI thread.
- If an open target disappears between display and click, report that exact
  failure and refresh the affected repository; do not silently open the folder
  instead.

## 5. UX and accessibility plan

### Settings → Roots

- Replace the disabled “add root” control with a real roots list and visible
  Add, Remove, Enable/Disable, Move Up/Down, Depth, and Ignore configuration
  affordances.
- Show path, enabled state, configured depth, current scan status, and a clear
  validation/permission warning for each root.
- Use a folder picker for selection; do not ask users to paste a path as the
  only flow. Keep the resolved full path visible for review.
- Removing a root requires a clear explanation that it removes that root from
  future scans, not its files or repositories. No root operation writes to the
  target directory.
- Keep the explanation for missing, inaccessible, or unsupported roots visible
  near the root row; disabled controls must explain why in visible text.

### Dashboard and Projects

- Search remains visible and usable by keyboard, with a clear button, match
  count, no-results state, and a non-destructive clear action.
- Add explicit status for cache freshness and current scan progress. Distinguish
  “cached and refreshing,” “fresh,” “partial,” “stale after error,” and “not
  scanned”; never render cached values as freshly measured state.
- Keep root identity available on cards when multiple roots contain similar
  repository names. Provide a stable path tooltip/accessible name without
  overloading the card with long paths.
- Use the existing WinUI list/grid controls and their virtualization rather
  than constructing one visual tree per project up front.
- Sort/filter updates must preserve selection when the selected checkout still
  exists. If it disappears, clear selection deliberately and show a useful
  state.
- Use skeletons for pending data only; no invented project names, scan counts,
  health badges, or demo-only rows.

### Worktree and workspace presentation

- Distinguish a worktree from a duplicate root discovery with text and
  automation names, not colour alone.
- Show the parent/common repository association only when local metadata
  validates it.
- Expandable solution/project/component rows must be reachable by keyboard and
  have automation names that identify the repository and target.

### Motion and responsiveness

- Keep transitions short and respect reduced-motion/system settings where
  available. Do not animate every refresh event or reflow all cards on each
  watcher notification.
- Debounce search input locally and independently from the filesystem watcher.
  Search does not perform I/O.
- Preserve the existing sea-blue theme, light/dark resources, 8 px corner
  radius, and Mica/title-bar behavior.

## 6. Test and verification plan

The roadmap estimates **+26 tests**. Treat that as a planning estimate, not a
quota: add the tests that prove the behavior and avoid redundant cases.

### 6.1 Headless service and model tests

1. **Root settings/projection:** legacy default, multiple roots, invalid depth,
   blank/malformed path, duplicate canonical paths, enabled state, order,
   unknown-key preservation, settings round trip, corrupt settings recovery,
   and migration behavior if a schema bump is justified.
2. **Ignore matcher:** fixed examples and table-driven cases for case,
   separators, wildcards, ordered negation, invalid syntax, defaults, depth,
   root-relative matching, and non-negatable safety invariants. Assert preview
   and scanner use the same decisions.
3. **Identity and worktrees:** `.git` directory/file, relative pointer,
   malformed pointer, missing/looping/escaping pointer, linked worktree,
   submodule, same checkout reached from two roots, two distinct worktrees of
   one common repo, and no-remote repositories.
4. **Root scanner:** independent depth/ignore rules per root, disabled/missing
   root, inaccessible directory, deterministic order, cancellation, bounded
   parallelism, partial failure, and no filesystem/Git writes or network calls.
5. **Catalog/progressive scan:** shared in-flight operation, immutable
   snapshots, progress sequencing, failed/cancelled refresh behavior,
   overlapping invalidations coalesced, one project update without scanning
   unrelated roots, and every subscribed page sees the same catalog revision.
6. **Cache:** schema round trip, legacy/missing cache, corrupt backup, future
   schema, invalid paths/records, duplicate entries, atomic write failure,
   stale/fresh provenance, cache followed by newer scan, stale fallback after
   failure, and zero Git calls before cached first paint.
7. **Watcher:** fakeable event source/clock for 500 ms debounce, event storm
   coalescing, create/delete/rename, overflow/full-rescan fallback,
   inaccessible root, cancellation/disposal, root reconfiguration, and no
   duplicate active watchers after Settings edits.
8. **Search/sort/saved views:** name/path/branch/version matching, empty input,
   case-insensitive behavior, stable tie order, root/favorite priority,
   progressive additions/removals, filter persistence, and invalid saved
   metadata recovery.
9. **Organization/workspace:** pin/tag/color round trip, recent-open only on
   successful action, missing project metadata cleanup policy, archived
   definition, component/solution detection and path-with-spaces open action.
10. **Scale/regression:** deterministic synthetic 50-repo SSD fixture, 100
    loaded-card memory measurement, current default ecosystem fixture, existing
    one-catalog-scan navigation guard, build badge/history independence, and
    source guards against blocking calls in UI-facing code.

Use temporary repositories/directories and injected time/filesystem/watcher
boundaries where the real clock or OS watcher would make tests flaky. Do not
mutate the user's checkout, actual settings, Git configuration, desktop, or
template in tests. No test may fetch/push or depend on GitHub credentials.

  Settings/Dashboard/Projects, and verify accessible names and state changes.

  expand a workspace, and verify visible validation/error state.
- Pass an isolated `DEVDESK_DATA_DIR`; use temporary roots/repositories; launch
  only the built test executable; close it in `finally`; capture logs on
  failure; never use the user's real projects as test fixtures.
- Keep FlaUI tests out of ordinary headless xUnit and the required CI job unless
  a reliable interactive Windows runner is explicitly available and approved.
  A local UI test command must be opt-in and document its desktop requirements.
- Keep `Scripts/smoke-ui.ps1` and `Scripts/verify-shell.ps1` as existing

  change; do not replace them with a FlaUI dependency by default.
- The user authorized implementation and UI testing. The opt-in FlaUI test was

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Overlapping roots show duplicate projects or hide valid worktrees. | Separate checkout path from common Git identity; resolve the worktree policy before implementation; test overlapping roots and multiple linked worktrees. |
| `FileSystemWatcher` emits duplicate/out-of-order notifications or overflows its buffer. | Treat events as invalidation hints, debounce/coalesce, reconcile on overflow/error, and periodically allow an explicit full refresh. |
| Cache contains stale branch/status/version facts. | Show cache timestamp/provenance, refresh in background, never overwrite a newer scan with cache, retain stale state on error, and keep manual refresh available. |
| Broad glob or negation unexpectedly traverses hidden/build/Git data. | Keep safety invariants separate, share matcher/preview code, use table-driven traversal tests, and show excluded-path previews. |
| One slow, unavailable, or network root stalls all roots. | Per-root/per-repo time budgets, bounded parallelism, cancellation, partial results, and explicit unsupported/slow-root warning. |
| More repositories create excessive watchers, events, or memory use. | One bounded watcher per enabled root, explicit disposal, event coalescing, bounded cache/card collections, virtualization, and M5 measurement. |
| `gitdir:` pointers are malformed or escape the expected metadata area. | Validate pointer syntax and target, reject traversal/loops, report per-item warnings, and never use pointer contents as shell input. |
| Settings schema expansion breaks hand-edited files or downgrade behavior. | Additive projection, unknown-key preservation, corruption backup, explicit schema tests, and no schema bump without a tested migration. |
| FlaUI desktop runs are flaky or cannot start WinUI in hosted CI. | Compatibility spike first; separate opt-in project; do not gate core tests on an unavailable interactive runner. |
| Scope expands into v0.8/v0.9 while implementing polish. | Keep the exact nine roadmap work items as the boundary; defer command palette, tray, onboarding, and general hardening. |

## 9. Proposed implementation sequence

1. Resolve the four behavior decisions in §2 (worktree rows, ignore precedence,
   supported root locations, and UI-automation execution surface).
2. Write characterization tests for current default-root scanning and settings
   compatibility before refactoring the scanner.
3. Implement root configuration/projection/UI and a pure scan configuration
   contract; prove the default root remains behaviorally identical.
4. Implement the shared ignore matcher and safe Git identity parsing; test real
   temporary worktrees and overlapping roots.
5. Introduce the catalog cache DTO and cache-first/fresh-scan states; preserve
   the one-catalog-per-process contract.
6. Add progressive immutable catalog updates, per-checkout invalidation, and
   root-scoped watcher lifecycle with injected time/event boundaries.
7. Implement dashboard/project search, sort, saved views, pin/tags/recents, and
   workspace expansion as projections/actions over catalog models.
8. Add scale guards, measure M1–M6, then perform the agreed opt-in UI automation
   spike/smoke and manual UX review.
9. Update roadmap/README/AGENTS and record exact test/build/performance/UI
   evidence before tagging.

No phase should proceed past an unresolved behavior choice if the choice affects
identity, scan safety, persisted-data compatibility, or whether UI automation
is permitted.
