## 1. Goal and release boundary

Make the existing version → notes → tag → CI → published-feed path operable
from DevDesk, while preserving the release script as the one implementation of
Velopack packaging and upload. The user sees the exact version, channel, tag,
notes, repository, and actions before any repository or remote mutation.

The flow is deliberately split into safe preview work and explicitly confirmed
execution. A preview never changes a project file, creates a commit/tag, pushes,
or calls a GitHub mutation endpoint. Committing a version, creating a tag, and
pushing are separate, reviewable actions behind the existing preview/confirm
pattern. A tag push is irreversible from DevDesk: the app must never force-push,
delete, or silently move an existing tag.

The release workflow remains responsible for verification and publication:
tag push triggers `.github/workflows/release.yml`; it runs the build/test gate
and then delegates packaging and feed upload to
`Scripts/build-and-release.ps1`. The app monitors that run through read-only
GitHub API requests. Cancel/retry actions open the appropriate GitHub page;
v0.6 does not add workflow-mutation API calls.

**Exit demo:** in a local DevDesk checkout, inspect a release preview, edit the
generated notes, explicitly confirm the version change and tag push, monitor
the release workflow, and see the resulting release/feed entry on the DevDesk
self page. Running the test suite or inspecting the preview must not open the
application window.

### Confirmed decisions

1. Reuse `ReleaseChannels`, `GitService`, `GitHubService`, `ProcessRunner`,
   `ActivityCenter`, `SettingsService`, and the existing release script/workflow.
2. Keep the four project version fields synchronized. Channel suffix remains in
   the informational version and tag; the numeric version is `X.Y.Z`.
3. Keep all Git, filesystem, HTTP, and process work out of XAML page code.
   Release orchestration belongs in testable services; UI only previews state
   and forwards confirmed commands.
4. The preview is read-only. Mutations require the same explicit preview and
   confirmation discipline as other Git writes. No test may mutate this real
   checkout or push/tag anything.
5. Tests use synthetic repositories, fake process/HTTP dependencies, and
   temporary project files. They do not use this machine's Credential Manager,
   network, installed app, FlaUI, or UI Automation.

### 3.1 Explicit non-goals

- Publishing without a user confirmation or automatically selecting a new
  major/minor version from commit text.
- Force-pushing, deleting/replacing a tag, deleting a release, rollback of a
  published release, or silently retrying an irreversible action.
- Multi-project/batch releases, draft editing on GitHub, arbitrary hosted git
  providers, or a new release framework/dependency.
- Reimplementing Velopack, invoking a second packaging path, or moving the

  cancellation, or workflow retry.
- FlaUI tests, screenshots, or opening windows without explicit user approval.
- Changing the active v0.4/v0.5 integration beyond what is necessary to wire
  the agreed release flow after those changes are settled.

## 4. Contracts and behavior

### 4.1 Channel and tag contract

`ReleaseChannel` is the typed internal representation; `ReleaseChannels` remains
the compatibility boundary for existing string settings, serialized values,
and view models. The canonical persisted/tag vocabulary remains `stable`,
`beta`, and `dev`; stable has no suffix, while beta/dev use `-beta`/`-dev`.
Unknown values, `alpha`, extra prerelease identifiers, and malformed versions
must be refused, not mapped to a default channel.

No settings schema change is needed for an enum: persisted channel values remain
strings and existing unknown-value fallback remains in `SettingsService`.

### 4.2 Version preview and writes

- The selected project must be the local repository whose root contains the
  validated project file and Git metadata. Do not accept an arbitrary path
  supplied by GitHub data.
- For a selected channel, use the numerically greatest valid version tag on
  that channel as the suggestion baseline. If there is no supported tag for
  that channel, use the project's current numeric `<Version>`. Do not borrow a
  tag from a different channel. The user can explicitly select patch, minor, or
  major; patch is the default.
- Preview displays all changed fields and the proposed notes/tag/channel before
  writing anything.
- The project version quartet is `Version`, `AssemblyVersion`, `FileVersion`,
  and `InformationalVersion`; all are updated as one filesystem transaction.
- Use a same-directory temporary file and atomic replacement where supported.
  Clean up only the exact temp file created by this operation. If replacement
  fails, preserve/restore the original and report failure.
- A prior tag must be checked locally before create, then rechecked by the
  push result. Never force or delete. A remote tag conflict stops the flow and
  reports the conflict; it does not attempt another version automatically.
- A version commit uses the existing safe Git argument-list boundary. No shell
  strings, credential argv, or `GITHUB_TOKEN` persistence.

### 4.3 Release orchestration

- The user reviews the complete operation preview. Version file write and
  commit/tag actions occur only after confirmation; pushing is a separate
  explicit action because it triggers CI/publication.
- Cancellation before push leaves no remote side effect. A cancellation or
  failure after push reports the remote tag as created and stops any attempt to
  undo it.
- Release work is represented in `ActivityCenter`; progress and result remain
  visible after navigation. Do not add a competing queue or duplicate history.
- CI monitoring is asynchronous, cancellable, selected-repository scoped, and
  bounded. It never waits on the UI thread, starts at app startup, or polls in
  the background after leaving the release surface.
- Every run link must be validated HTTPS GitHub.com and comes from a validated
  API response. Never construct an action URL from untrusted repository fields.
- The monitor remains read-only. Browser cancel/retry links are clearly
  external actions and do not imply that DevDesk executed them.

### 4.4 Secrets and diagnostics

- Reuse the v0.5 credential boundary; do not copy the PAT into settings,
  release history, `ReleaseNotes.md`, command arguments, process output, or
  logs.
- If the release script requires `GITHUB_TOKEN`, provide it only through the
  process environment injection boundary and never log the value.
- Do not record raw API response bodies, authorization headers, or notes
  contents in diagnostic logs. Release history stores safe metadata only:
  project identity/path, version/channel/tag, timestamps, status, and safe
  links/log path.

## 5. UX state matrix

| State | Required behavior |
|---|---|
| Unsupported/non-GitHub repository | Show why release monitoring is unavailable; never guess a remote. |
| Dirty tree or version mismatch | Show a blocking reason and exact files; no commit/tag/push command is run. |
| No previous release/tag | Offer an explicit first-release path; do not invent a baseline or infer a bump. |
| Preview | Show project, current/proposed version quartet, channel, notes, commit, tag, remote, and irreversible effects. No writes. |
| Version write/commit failed | Preserve source bytes where possible; report failed step and whether any local commit/tag exists. |
| Tag exists locally/remotely | Refuse; do not move, overwrite, delete, or automatically choose another tag. |
| Push confirmation | Name the exact tag and remote and state that push triggers CI/release publication. Require a second user action. |
| CI queued/running | Show state, run link, elapsed time, and cancel-monitor option; no fabricated progress percentage. |
| CI success | Show run link and release link only after a successful response confirms the release/feed entry. |
| CI failure/cancel/timeout | Show actual status and validated GitHub run link; do not retry automatically. |
| Offline/rate limited | Preserve last valid state with timestamp; distinguish offline from 401/403/404/rate limits. |
| No release history | Show a successful empty state only after the API/feed request succeeds. |

## 6. Implementation sequence and gates

1. **Foundation (complete):** typed channel representation retains string
   compatibility and has pure xUnit coverage.
2. **Bump policy (resolved):** patch is the default; the user may choose patch,
   minor, or major. Baseline is the greatest valid tag on the selected channel,
   falling back to the current project version.
3. **Pure release core:** strict version/tag validation, numeric ordering,
   validation, notes
   formatting, and safe release-plan DTOs; fake/time-based unit tests only.
4. **Atomic file operation:** harden version bump script/service with injected
   failure tests against temporary project copies.
5. **Execution boundary:** use existing Git/process/ActivityCenter contracts;
   verify command construction and failure/cancel boundaries with fakes.
6. **Monitor and channel alignment:** implement GET-only polling with bounded
   backoff; align script and CI tag validation; no real GitHub requests in
   tests.
7. **UI and release timeline:** wire view models and XAML only after the service
   contracts pass; keep all irreversible actions previewed and confirmed.
8. **Headless validation:** targeted xUnit tests first, then build and the
   repository's headless `dotnet test DevDesk.Tests -p:Platform=x64` gate as
   appropriate. Do not run `smoke-ui.ps1`, `verify-shell.ps1`,
   `capture-page.ps1`, FlaUI, or any executable that opens a window without
   explicit user approval.
9. **Release gate:** the user explicitly requested commit, push, and release
   only if all gates pass. Keep predecessor-release and dogfood requirements
   in force; do not create the v0.6 tag while those prerequisites remain open.

## 7. Test plan (desktop-safe)

All tests belong in `DevDesk.Tests/`. They run as ordinary xUnit tests and may
compile WinUI references but must never launch DevDesk or attach UI Automation.
Scripts are executed against temporary fixtures only. No test performs network
access, GitHub writes, real tags/pushes, or reads credentials from Windows.

| Area | Coverage |
|---|---|
| Channel model | enum ↔ stable/beta/dev string mapping, legacy API equivalence, default beta, tag suffixes, retired/unknown suffix rejection. |
| SemVer | strict three numeric components, no leading zeroes, valid prerelease subset, numeric comparison (`1.10.0` > `1.9.0`), stable > prerelease, beta/dev ordering, invalid/unsupported tags. |
| Suggestion | default patch and explicit patch/minor/major increments; numeric ordering, selected-channel filtering, current-version fallback, invalid baseline, leading zeroes, channel suffix construction, integer overflow. |
| Version file | four-field synchronization, suffix handling, idempotency, missing/duplicate property rejection, temp-file replacement, injected failures preserve original bytes. |
| Release notes | grouping, ordering, multiline/empty subjects, safe PR links, escaping, deterministic output, tag-range isolation, no-tag first release, empty range, invalid/missing tag, bounded history. |
| Release plan | exact git argument arrays, no shell interpolation, no force/delete, refuse existing tag, push only after explicit confirmation, stop after failure/cancellation; temporary local repositories only. |
| CI monitor | fake HTTP/time provider, exact SHA/tag match, state transitions, bounded exponential backoff, cancellation, timeout, 304/cache/rate limit, safe links, unrelated run ignored. |
| Release view | fixture-backed stable/beta/dev data, no sample rows, stale and empty states, cross-repository isolation. |
| Window safety | source guard ensuring new test/production release paths do not call `Process.Start` for the app, FlaUI/UIA, or smoke scripts; test command is `dotnet test` only. |

Feature logic remains covered by headless tests. The existing navigation and
shell verification scripts may open windows and were run only after the user
explicitly approved them. FlaUI was not used.

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Irreversible tag triggers workflow and publication | Exact two-stage preview/confirmation; no force/delete; exact remote/tag visible. |
| A second release implementation drifts from CI | Script remains the packaging/upload authority; app triggers existing workflow only. |
| Version file left partially changed | Same-directory atomic replacement and injected failure tests; no project writes in tests. |
| Wrong bump suggested | Do not implement an implicit algorithm before user policy choice; always allow validated explicit override. |
| Wrong workflow monitored | Require selected repository + exact tag/head SHA + workflow identity; ignore unrelated runs. |
| API outages/rate limits | Bounded polling/backoff/cancellation; honest stale/error state; no hidden retries. |
| v0.4/v0.5 changes conflict | Do not modify their pending integration; merge/validate those changes before release UI wiring. |
| Test interrupts user | Keep logic tests headless; run UI smoke/shell automation only with explicit user approval. |
